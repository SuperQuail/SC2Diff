# 协作功能规划（第二阶段）

> 第一阶段（本地闭环 + 速度优化）已完成并通过测试，见 [../README.md](../README.md)。

## 0. 起点：现在已经有什么

- 对象模型：blob（zlib，内容寻址）+ commit（tree 内联在提交 JSON 里，parents[] 支持多父）
- 引用：refs/heads/*、refs/tags/*、符号 HEAD、detached HEAD
- 暂存区：.sc2diff/index.json，同时充当 stat 缓存
- 历史算法：merge_base() 已能算最近公共祖先（合并的前提已经就位）
- 语义 diff：身份键模型（Objects / Triggers / Catalog 等）
- 容器：pack 输出经编辑器 A/B 验证可正常打开

缺的是三块：**合并**、**打包压缩**、**远端**。

## 1. 语义三方合并（M1，优先级最高）

### 为什么它最值钱

文本合并两份被编辑器整体重写过的 XML 会满地冲突；而我们的模型是「身份键 -> 字段」的字典，
三方合并退化成三件很干净的事：

| 情形 | 处理 |
| --- | --- |
| 改动集不相交（不同组件） | 直接取两边的结果，**零冲突** |
| 同一组件、不同实体 | 实体级合并，**零冲突** |
| 同一实体、不同字段 | 字段级合并，**零冲突** |
| 同一字段两边都改且不同 | 冲突，精确定位到 组件 / 实体 / 字段 |
| 一边删实体、一边改实体 | 冲突（删改冲突） |

### 实现要点

1. 以**我们的版本为基底 DOM**，只把对方的差异应用上去，而不是重新序列化两边。
2. 路径解析复用 sc2semantic 的身份键规则（Index/Id/Type 优先，无身份才退回位置下标）。
3. 冲突**不写冲突标记**：在 XML 里插入尖括号标记会直接让地图无法加载；
   改为把冲突写进 .sc2diff/MERGE_HEAD 与 .sc2diff/CONFLICT.json，工作树保留 ours，退出码 1。
4. 配套命令（与 git 同名）：

    sc2diff merge <rev> [-m msg]
    sc2diff merge --abort
    sc2diff merge --continue
    sc2diff checkout --ours   <component>
    sc2diff checkout --theirs <component>

### 无法字段级合并的组件

二进制组件（DocumentHeader / MapInfo / t3HeightMap / 贴图模型）**不支持三方合并**。
策略：两边都改同一个二进制组件 -> 直接冲突，要求人工选择；两边改不同组件 -> 正常合并。

## 2. 打包压缩与 GC（M2）

### 现状问题

每个 blob 整体 zlib 存储，没有 delta。175 MB 的工作树改 10 次就是 10 份完整副本，
而真正的改动可能只有几 KB。

### 目标

1. **packfile**：把所有可达对象写进一个 objects/pack/pack-<id>.pack 加 .idx；
2. **delta 压缩**：同族对象（同一组件的历史版本）生成 delta；
   文本可用 zstd --long，二进制可用前缀/后缀 diff 加指令流；
3. sc2diff gc：回收不可达对象、把松对象合并进 pack；
4. 保留松对象作为**写入路径**（一次提交一个 blob），gc 时才打包 —— 与 git 一致。

### 预期收益（估算，需实测）

文本类组件（GameData XML / Triggers / 本地化 txt）delta 收益高，预计 5-20x；
二进制资源（.dds/.m3/.tga）收益低，只能靠**内容寻址去重**（同一贴图多版本共用 blob）。

## 3. 交换与协作（M3）——**已决定：不做远端协议，改做补丁包**

### 3.1 为什么不做 git 式远端

push/pull/clone 需要一个**服务端**。本项目没有 GitHub 类托管，也没有已知的共享盘或 Web 服务器。
一个没人能托管的协议没有使用价值。远端不是「还没做」，而是**当前条件下不该做**。

后续若出现下列任一条件，再考虑 M3-remote（届时复用 bundle 的对象格式即可，不会返工）：
- 有共享盘 / NAS / 内网服务器；
- 启动器要托管官方战役库。

### 3.2 做什么：bundle（补丁包）——**已实现并验证**

    sc2diff bundle <out.sc2bundle> [--refs <name>...] [--basis <rev>...]
    sc2diff apply  <file.sc2bundle> [--no-refs] [--no-checkout]
    sc2diff unbundle <file.sc2bundle>        # apply 的别名

**bundle 就是一个 zip**：内含 `manifest.json`、`commits/*.json`、`objects/*`。
这样它能走你们**现有的所有渠道**（网盘、群文件、共享目录、启动器解压），零基础设施改造，
并且用任何解压工具都能查看内容。

`--basis <rev>` 生成**瘦补丁**：把 basis 里已有的组件 blob 全部排除，只发对方没有的东西。
apply 时会校验前置提交是否存在，缺失则明确报错（不会写出半个仓库）。
apply 成功后按 ref 情况自动处理：

| 本地 ref 状态 | 动作 |
| --- | --- |
| 不存在 | 创建，并在工作树干净时**自动检出**（等价于 clone） |
| 是对方的祖先 | fast-forward，同样自动检出 |
| 已分叉 | 只导入对象与提交，提示 `sc2diff merge <name>` |

### 3.3 实测收益

| 场景 | 体积 |
| --- | --- |
| 44.0 MB 战役包（UmojanCT.SC2Mod） | 44.0 MB |
| 完整历史 bundle（2 个提交、299 个组件） | 49.2 MB |
| **改 1 个 XML 组件的瘦补丁** | **0.02 MB（约占归档 0.05%）** |
| paiur01 场景：完整 bundle vs 瘦补丁 | 1391.7 KB vs **35.0 KB**（40x） |

瘦补丁实际只装了 **1 个对象**（被改的那个组件），其余全部来自对方已有的 basis。

### 3.4 对启动器的意义

这是本项目对产品最直接的收益：**增量更新**。
改一个 XML 只需下发几十 KB，而不是让玩家重下 100 MB 的战役包。
补丁包本身是 zip，启动器现有的解压/校验链路可以直接复用；后续只需要
「repo 存在则 apply，不存在则整包安装」这一条分支。

### 3.5 仍然需要合并

bundle 解决「怎么把改动送过去」，**不解决「两边都改了怎么办」**。
上表第 3 行（已分叉）唯一给出的动作就是 `merge`，而 merge 还没实现。
所以 M1（语义三方合并）依然是协作链路上真正缺的那一环。

## 4. 风险与必须提前决定的事

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| **合并后引用完整性** | 组件之间有 id 引用（触发器引用单位 id、目录条目互相 Link）。字段级合并可能产生「指向不存在的 id」。 | 合并提交前跑一次**引用一致性校验**；不通过就降级为冲突 |
| **地图是整体，不是文件集合** | 地形栅格、MapInfo、DocumentHeader 无法字段级合并 | 明确策略：二进制组件两边都改即冲突，并写进文档 |
| **版本侧车** | *.version 记录组件最后修改时间，合并后可能与内容不一致 | 合并后按内容重算这些 sidecar（44 字节结构已掌握） |
| **大仓库膨胀** | 没有 delta 前，每次提交都存完整变化组件 | M2 优先于 M3 |
| **冲突体验** | 冲突发生在实体/字段级，CLI 表达力有限 | M4：GUI 三栏对比 |
| **并发写** | 两个进程同时操作同一仓库无锁 | 引入 .sc2diff/index.lock（git 同款） |

## 5. 里程碑与验收判据

| 里程碑 | 内容 | 验收判据 |
| --- | --- | --- |
| **M1 语义合并** | merge / --abort / --continue / --ours / --theirs | 改动集不相交的两条分支合并后**零冲突**；冲突时能精确报出 组件/实体/字段；合并提交后 pack 出的地图仍能被编辑器打开 |
| **M2 pack + gc** | packfile、delta、gc | 10 次提交后 .sc2diff 体积目标下降 >=5x；gc 后所有历史仍可 checkout |
| **M3a 共享目录远端** | clone/fetch/pull/push | 两个目录互推互拉，历史与内容完全一致 |
| **M3b 哑 HTTP** | 静态服务器上的 bare 仓库 | 能 clone 与 fetch |
| **M4 冲突 GUI** | Tauri 三栏合并视图 | 人能在一个界面里解决冲突并提交 |

---

## 6. 建议的下一步

**先做 M1（语义三方合并）。** 理由：

1. 它是多人协作的真正门槛 —— 没有合并，分支就只是快照；
2. 身份键模型让它在**语义层**变得可控，这是相对 git 的结构性优势；
3. merge_base() 已实现，剩余工作集中在「把对方的差异应用到我们的 DOM」；
4. 完全不依赖网络，能立刻在单机验证，风险最低。
